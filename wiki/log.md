# Log

## 2026-08-26

* **Create**: [A sixteen-bit address computation that emits thirty-two-bit code](/observations/word-plus-integer-is-longint/observation.md). `YOfs[Y] + X` with a Word row table and an Integer column is a LONGINT, because neither operand type holds every result -- so the most natural pixel-address line in a blitter compiles to eleven instructions with a CWD, a register pair and an ADC where the original has three and one ADD, and the final MOV discards the half that forced the widening. Worth writing down for the tell, which is cheap and general: a sign- or zero-extension instruction INSIDE an address computation, on a machine whose addresses are sixteen bits. Carries the table of give-aways, the three possible answers (match the types, cast the sum, or the routine was assembler) and the warning not to reach for the cast first -- on this target an added LongInt cast in a neighbouring expression measured WORSE, because it forced the runtime's 32-bit multiply. Also carries the version that is not merely bigger but WRONG: ours emitted MUL / CWD / IDIV where the original has CWD / IMUL / IDIV, and the CWD after a MUL overwrites the product's high half before the divide sees it. A probe spelling the expression eight ways across three compiler releases matched in none of the twenty-four builds.

* **Extend**: `spanwhy.py` now passes `--min` through to `spans.py` instead of inheriting its default of sixteen. The tool answers "is this span real work or an address that moved?" and it could only answer it for spans of sixteen bytes or more -- so a part whose largest span was fifteen got "spans.py ran and reported no span" while carrying a hundred bytes of difference. It matters more than a convenience: on one target the address-only class lived almost ENTIRELY in the small spans -- twenty one-byte spans, all twenty the same far call to a runtime routine at a different offset -- so the question was being asked exactly where the answer was already known.

* **Create**: [Every instrument reads clean and the screen is blank](/observations/name-resolution-is-invisible/observation.md). A scene entry point grew a local `F : file` and opened that, while the routine doing the reading used the unit-level `F` of the same name, which nothing ever opened. With I/O checking off both BlockReads failed silently, the DAC took 768 bytes of uninitialised stack and the screen buffer was never filled -- a flat red screen and nothing else. Worth writing down because of what the instruments did: the coverage walk read 99.0% before the fix and 99.0% after, the initialised image compared identical both ways, the trap streams identical both ways, the lint pass clean at 67 files. Every one of them measures BYTES, and the defect was in which object a spelling resolved to, which is a property of the program's structure that a byte compare abstracts away by construction -- the shadowed reference is `[BP-n]`, so it does not even produce a row for the reference map to pair. The general family is "the right code operating on the wrong object": shadowed variables, a `with` binding a different record, a qualified name resolving to the other unit's export. For that family the order of work inverts -- the run is the DETECTOR and the measurement only says the repair cost nothing. The second thing that sees it is the original's prologue: PUSH BP / MOV BP,SP with no ENTER means the routine has no locals at all, so there is no local to have and the question closes before it is asked. Carries the honest blind spot, which is that the observation gives no way to FIND these -- only that the instruments cannot, and that a run is expensive enough that it belongs after a change moving a declaration between scopes rather than after everything.

* **Create**: [The operand it evaluates first is the one written second](/observations/operands-evaluate-backwards/observation.md). With both operands of a binary operator needing the accumulator, Borland computes one, parks it in DX, computes the other into AX and adds -- and the one it parks is the operand written SECOND in the source. Worth writing down because the intuition points the other way and inverting it by hand every time is exactly the step that gets skipped. Found on a lens-table builder holding sixteen expressions of the form `(row + 20) * 40 + (col + 20)`, all written the natural way round, all four bytes displaced, five separate fifteen-byte spans to show for it; rewritten with the terms swapped it closed 163 bytes in one build. Carries when there is nothing to read (a simple right operand is added in place) and the blind spot that a differing operand order can equally be a TYPE difference -- check the addressing as well as the register.

* **Create**: [The original contains code that does nothing, and you have to put it back](/observations/the-original-does-nothing/observation.md). Three instances in one target in one day -- forty-nine iterations of two conditional self-assignments, two dead tests inside a live loop sixteen hundred times over, and eight separate declarations of storage that is never touched. A reconstruction written cleanly from an understanding of what a routine DOES cannot invent any of them, and the absence has no shape to look at, so no amount of re-reading the source finds it. The frame check catches the dead DECLARATIONS, because the ENTER operand counts them; nothing declaration-driven can see a dead STATEMENT. What finds them is the disassembly read with one discipline: when a sequence appears to do nothing, do not assume you have misread it -- check the operands, then believe the bytes. Carries the reading rule (a store and a load of one address with nothing between; a conditional whose taken branch reproduces the fall-through's state; an arithmetic identity operand, which was a variable once because the compiler folds constants) and the blind spot, which cuts both ways and is expensive in the other direction.

* **Extend**: [A folded subscript names its bounds](/observations/subscript-fold-names-the-bounds/observation.md) with the failure mode that closes an investigation rather than delaying one. A span had been read, understood and written off as "a register-allocation difference, deliberately left -- the original builds the index in DI, ours in AX and then transfers; Pascal does not name the register". Every clause of that is a true observation and the conclusion is wrong: the original built the index in DI because it was building a TWO-dimensional subscript, and the register followed from the type. Declaring the second dimension closed the span to zero. Also carries the recurring case -- one corpus produced the same flat-versus-two-dimensional palette defect in three unrelated units on one day, so a 768-byte DAC buffer is worth declaring as [0..255, 0..2] first and flat only when the binary shows the multiply and the add done separately.

* **Create**: [The total balances and the layout is still wrong](/observations/balanced-total-hides-order/observation.md). Written because two instruments called a data segment finished for days -- the initialised image byte-for-byte identical, the header's allocation matching to the paragraph -- while thirty-two bytes sat on the wrong side of a unit boundary and a compensating error thirty bytes the other way kept every total exact. A sum cannot distinguish an ordering. What can is a per-reference shift map, where a BOUNDED run of one non-zero shift with zero either side is the signature of a misplaced block, as against a single uniform shift below some address, which is a size defect. The cause was an arithmetic slip in a COMMENT, and the note beside it had hedged correctly and been ignored: "do not treat the 98 as a declaration that has been read -- it is a total that balances", next to thirty bytes it could not account for. The unaccounted remainder was the whole finding. And the correction pays twice: the compensating number, once it could be read off two measured addresses instead of bisected, came out at 128, which is a file record.

* **Create**: [Two bytes the compiler cannot emit](/observations/instruction-the-compiler-never-emits/observation.md). The usual tells for hand assembler are positive -- a string instruction, `LOOP`, register-passed arguments -- and a routine made of constant stores and near calls has none of them. This runs the idea backwards: seven spellings of "count down and stop at zero", across Turbo Pascal 7, 6.0 and 6.1, and `DEC [mem]` followed straight by `JNE` came out of none of them. What the negative unlocked was not the five bytes but the reading of everything round them: an `OR DX,DX` that no Turbo Pascal calling convention explains, and a `JE` over a `JMP` that is what a person writes when the exit is out of short reach. Both tells had been seen for weeks and each had a plausible innocent reading on its own.
* **Create**: [Code past the initialisation section came from an object file](/observations/code-after-the-init-section/observation.md). A unit's `begin` block is its last declaration, so a routine at a HIGHER offset than the initialisation code did not come from the Pascal at all. Written for the second half rather than the first: an object is linked per MODULE where Pascal is smart-linked per PROCEDURE, so a routine nothing in the image calls still ships -- and reconstructing such a routine as Pascal fails however well it is transcribed, in a way that looks like a transcription problem. The rule was already written down in another unit of the same target while this one was being read as though the uncalled routine could not exist.
* **Extend**: [The frame is bigger than your locals account for](/observations/frame-size-counts-locals/observation.md) with the cost of `with`. Four bytes of frame for the record's address, and the address computed ONCE -- so an original that recomputes an element's address for every field it touches has no `with` in it. Both halves measure the same source line, and the frame is the cheaper of the two to read.

* **Create**: [The code is full of INT 34h and you conclude something about the coprocessor](/observations/n-and-e-are-different/observation.md). Written because this project got it wrong TWICE: $N decides whether 80x87 instructions are emitted at all, $E decides whether they ship as themselves or as INT 34h..3Dh traps, and a trap is evidence of the second and of nothing else -- least of all of the hardware the author had, since the runtime patches them at startup only where a coprocessor is present. The unit comment that misled the second attempt said "is x87 code" and listed the instruction encodings without mentioning that they ship as traps: accurate, incomplete, and the incompleteness was the load-bearing part.
